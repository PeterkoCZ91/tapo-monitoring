# Tapo C100: verified behavior and integration limits

These notes cover **C100 hardware 4.0, firmware 1.9.1 Build 260519 Rel.2746n**, a fixed,
mains-powered, Wi-Fi single-lens camera. The [anonymized report](../tests/fixtures/cameras/c100-1.9.1.json)
is a regression fixture. Results describe this tested hardware and firmware only.

## What it is and is not

| Area | Observed result |
|---|---|
| Lens | Fixed. No motor, presets, auto-track, `pan_limit`, ONVIF PTZ, floodlight or white lamp. |
| Night vision | Infrared only (`inf_night_vision`), day/night `auto`. |
| Video | Main H.264 1280×720 (about 16.75 fps, capable of 1920×1080 and H.265), sub H.264 640×360; PCMA audio 8 kHz mono. `stream3` does not exist. |
| Detection getters | Motion, person, tamper and baby cry readable. Vehicle, pet, line crossing, bark, glass break, meow, auto-track and smart-track return `-40101`. |
| Recording | Event-triggered plan all week (`0000-2400:2`); needs an SD card. |
| Not present | Battery, ring/chime, PIR, floodlight, siren hardware, `staticIp`/`quickSetup`/`nvmp`-style methods (`-40210`). |

## Events, clips and polling

- **Without an SD card** `searchDetectionList` and `searchDateWithVideo`-style reads return
  `-71114` (`STORAGE_NOT_EXIST`): there is no event path. With a card, `getEvents` works.
- Events carry **`alarm_type=2` only** (motion) and no `events_1` field. This model has no person
  bit, so use `event_profile: default` (typeless entries are motion candidates for the scorer) and
  leave the person decision to the scorer. A person-triggered `alarm_type` was not observed.
- `getEvents` is cheap: 12 polls over a minute took 6–25 ms each, no errors. Login plus the first
  call took about 3 s. Keep to one API session per camera (a second one risks `-40214`).
- A clip downloads over port 8800 with the same client (the cloud password equals the API
  password): a 15 s window took about 21 s and decoded to H.264 1280×720 plus AAC. Reuse the poller
  client rather than opening another session.
- A card that was used in another Tapo device keeps that device's index entries until they are
  overwritten, so events from before the card was inserted can come from the other device.

## RTSP and ONVIF

- RTSP needs a **Camera Account** (app: *Advanced settings → Camera account*); port 554 refuses
  connections until one exists. That account does **not** work for the pytapo API, which uses the
  Tapo account credentials, so configure `rtsp_user_env` / `rtsp_password_env` separately.
- ONVIF on port 2020 answers with a WS-UsernameToken digest: services device, deviceIO, events,
  media, analytics and imaging; profiles `profile_1` (1280×720), `profile_2` (640×360) and
  `profile_3` (JPEG 640×360). No PTZ. `GetProfiles` has to go to `/onvif/service`.

## Config sketch

```yaml
- name: c100
  host: 192.0.2.40
  user_env: TAPO_USER
  password_env: TAPO_PASSWORD
  rtsp_user_env: TAPO_RTSP_USER
  rtsp_password_env: TAPO_RTSP_PASSWORD
  sd_snapshot: true
```
