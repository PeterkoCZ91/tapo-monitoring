# Tapo C216: verified behavior and integration limits

These notes cover **C216 hardware 1.0, firmware
1.3.2 Build 260820 Rel.65461n**. The [anonymized report](../tests/fixtures/cameras/c216-1.3.2.json)
is a regression fixture. Results describe this tested hardware and firmware, not
every C216 revision or a completed fleet soak.

## Verified paths

| Area | Observed result |
|---|---|
| Capability report | 22 probes available, six rejected, one deliberately skipped. |
| Detection getters | Motion, person, baby cry and tamper available. Baby cry and tamper enable switches accept writes and can be read back; physical detection triggers are not yet validated. |
| Rejected detection getters | Vehicle, pet, line crossing, bark, glass break and meow return `-40101` with the tested wrappers. |
| RTSP | Main H.264 2304×1296 and sub H.264 1280×720, both configured at 15 fps; PCMA audio at 8 kHz mono. These are observed stream settings, not a maximum-frame-rate claim. |
| SD | Card status and recording plan readable; event index works with an initialized card. A recorded segment downloaded, aligned to its actual bounds, and yielded frames accepted by the scorer. |
| Motor and presets | Native movement, temporary preset creation/recall/removal and ONVIF position reads work. All four advertised pan/tilt endpoints were reached, followed by a verified return. |
| Day/night and light | Forced day/night settings accept writes and return to automatic mode. White-light status and `reverseWhitelampStatus` work; the `force_wtl_state` getter variant is unavailable. |
| Privacy | The switch accepts writes. RTSP can remain available while returning black frames; a successful stream probe does not prove privacy is off. |
| App notifications | The enable switch accepts writes and reads back. Mobile delivery and phone-side Do Not Disturb behavior were not tested. |
| Alerts and recovery | A fresh camera event passed through the daemon, RTSP capture, scorer and Telegram. The daemon also recovered events and RTSP after a controlled camera reboot. |

## Events and automatic SD rescue

The sampled single-lens events contain `alarm_type=2` or `alarm_type=6` but no
usable `events_1` person bit (the raw field is absent or null in the saved
samples; the decoder treats a missing/null value as zero for bit decoding and
the audit log prints `events_1=0`). They currently use
`event_profile: default`, which classifies these typeless entries as motion
candidates for the scorer. The value 6 alone is not an accepted C216 person
mapping: other models' event tables are not evidence for it.

This has a practical consequence: the SD rescue path for a failed or empty live
frame requires a confirmed-person classification or eligible PIR-backed motion.
These sampled motion candidates provide neither signal. **A successful direct
SD download does not establish automatic SD rescue for this model.** Controlled
person and motion samples must establish the mapping before changing its profile.

Without an SD card, the event-index call returned `-71114`. ONVIF PTZ support does
not establish a working ONVIF event source or a supported card-free daemon setup.

## Tracking and software boundaries

Turning native tracking ON/OFF and reading the state back works. This does not
establish person-only tracking, even if SmartTrack fields are returned.

In controlled native motor moves with tracking enabled, the standalone stop guard
detected the boundary and received Stop acknowledgements and verified tracking OFF,
but observed positions crossed the configured limits in both directions. This
occurred with both a 0.10 margin and the default 0.15 margin.

Those tests injected native movement; they did not observe a person-driven chase
or exercise the daemon's complete urgent-home recovery. They establish a boundary
finding, not safe tracking confinement. Reaching the mechanical travel endpoints
and returning to a preset does not validate software stops.

## Control and capability details

- An enable-only baby-cry or tamper write changed the returned sensitivity enum.
  Restore the sensitivity explicitly and read back the complete setting when testing.
- `-40101` can mean an invalid parameter as well as an absent feature. The runtime
  skips the irrelevant vehicle-OFF repair only for this exact verified hardware and
  firmware when its vehicle getter also returns that error. The twin reports
  `unsupported`; a working getter, another firmware, or a transient error does not
  disable normal repairs.
- The daemon can use separate `rtsp_user_env` / `rtsp_password_env` credentials.
  The report command's `--rtsp` probe uses the same account supplied for its API
  report, so those daemon settings do not change that command's credentials.
- The digital twin starts before the first event poll and captures refreshed
  evidence at `observability.probe_interval` (900 seconds by default). A short run
  may still show unknown event/media layers until a later probe.

## Still to validate

Controlled person-versus-motion mapping, automatic SD rescue, actual person-driven
tracking and urgent-home recovery, real darkness and night detections, physical
baby-cry/tamper triggers, longer network or power interruptions, and a completed
soak remain separate acceptance gates. No safe-tracking or fleet-readiness claim
follows from this report alone.
